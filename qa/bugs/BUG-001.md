# Reporte de Bug: BUG-001

**ID**: BUG-001  
**Título**: Apuestas bloqueadas indefinidamente al posponer, cancelar o suspender un partido  
**Tipo**: Bug Funcional  
**Severidad**: Alta  
**Prioridad**: Crítica  
**Módulo**: Admin / Liquidación de Partidos (`admin/partido_editar.php` & Base de Datos MySQL)  
**Ambiente**: PHP 8.3.1, MySQL 8.0 / MariaDB, Windows  
**Estado**: Resuelto (v3 confirmado con `resultados_concurrencia_v3.log`: 50/50 corridas exitosas, retry disparándose del lado Admin correctamente)  
**Fecha de Resolución**: Septiembre 2026  

---

## 1. Descripción del Problema Original

Cuando un administrador cambiaba el estado de un partido a **`pospuesto`**, **`cancelado`** o **`suspendido`**, las apuestas de dicho partido permanecían en `estado = 'pendiente'` de forma permanente. El saldo descontado a los usuarios al apostar quedaba retenido indefinidamente sin generar reembolso ni existir opción de anulación.

---

## 2. Causa Raíz (Análisis Técnico)

El trigger `trg_partidos_resolver_apuestas` evaluaba exclusivamente `NEW.estado = 'finalizado'`, ignorando cambios a `pospuesto`, `cancelado` o `suspendido`. Además, no existía un Stored Procedure de reembolso atómico en MySQL.

---

## 3. Solución Aplicada (Fase 1)

1. **Stored Procedure `sp_reembolsar_partido` en MySQL**:
   - Cursor sobre apuestas `WHERE id_partido = p_id_partido AND estado = 'pendiente'`.
   - **Orden Unificado de Locks**: Bloquea `usuarios` primero (`FOR UPDATE`) y luego actualiza `apuestas`.
   - **Guarda Atómica `ROW_COUNT()`**: Solo si `UPDATE apuestas SET estado = 'cancelada'` altera >0 filas se acredita el dinero a `usuarios.saldo` e inserta la fila en `transacciones`.
2. **Trigger `trg_partidos_resolver_apuestas` Idempotente**:
   - `ELSEIF NEW.estado IN ('pospuesto','cancelado','suspendido') AND OLD.estado NOT IN ('pospuesto','cancelado','suspendido') THEN CALL sp_reembolsar_partido(NEW.id);`

## 5. Hallazgo Adicional: Deadlocks por Foreign Key (18% de corridas)

**Causa Raíz Real**: La clave foránea `apuestas_ibfk_2` (`apuestas.id_partido` -> `partidos.id`) provoca que MySQL InnoDB adquiera un bloqueo compartido (Shared Lock) de forma implícita sobre la fila padre en `partidos` cada vez que se actualiza una fila en `apuestas`. Esto genera una espera circular inevitable cuando el Admin ejecuta `UPDATE partidos` mientras el Cliente ejecuta `UPDATE apuestas`.

### 5.1 Fase 6 (v2) — Fix incompleto: retry solo del lado que nunca lo necesitaba

**Solución aplicada en Fase 6**: Mecanismo de reintento (retry logic) con reintentos limitados (maxIntentos = 3) y backoff aleatorio (`usleep(random_int(50000, 150000))`) ante `PDOException` código `40001` (InnoDB Error 1213), agregado únicamente en `worker_cliente.php` / `mis_apuestas.php` (lado Cliente).

**Por qué v2 no resolvió el problema real**: al revisar `resultados_concurrencia_v2.log` línea por línea, las 6 corridas con deadlock (`DL = SI`) mostraron **6/6 casos como `ADMIN_ERROR`, 0/6 como error del lado Cliente**. En este escenario concreto (Admin pospone el partido mientras el Cliente cancela su apuesta), MySQL InnoDB elige consistentemente al Admin como víctima del deadlock, nunca al Cliente. El retry agregado en el lado Cliente era código muerto para este escenario: nunca llegó a ejecutarse porque el Cliente nunca perdía la transacción. Esto explica por qué la mejora de 41→44 corridas exitosas no tenía un mecanismo causal verificable — fue una mejora sin relación directa con el fix aplicado.

Este hallazgo es en sí mismo una demostración de rigor de QA: detectar que un fix "funcionó" en el número final pero no por la razón esperada, y corregirlo, vale más para un portafolio que ocultar el paso en falso.

### 5.2 Fase 6.1 (v3) — Fix real: retry en el lado que efectivamente pierde el deadlock

**Solución aplicada**: se agregó la misma lógica de retry (3 intentos, backoff aleatorio 50-150ms, detección de `PDOException` `40001`) a:
- `qa/scripts/worker_admin.php`
- `admin/partido_editar.php`, en el bloque `UPDATE partidos SET estado = ?` (acción `estado`) — el fix que realmente importa en producción, ya que antes un cambio de estado del admin podía fallar silenciosamente por un deadlock sin ninguna indicación de reintentar manualmente.

Ambos puntos loguean explícitamente el número de intento en el que se logró el éxito (`ADMIN_SUCCESS (intento N)` en el worker; `error_log` en `partido_editar.php`), para poder distinguir "éxito directo, sin deadlock" de "éxito solo gracias al retry (intento 2 o 3)" — esa distinción es la evidencia causal de que el fix funciona, no solo el número final de corridas exitosas.

### Comparativa de Ejecución de Concurrencia Real (v1 → v2 → v3):

| Métrica | v1 — SIN retry (`resultados_concurrencia.log`) | v2 — Retry mal ubicado, solo lado Cliente (`resultados_concurrencia_v2.log`) | v3 — Retry en AMBOS lados (`resultados_concurrencia_v3.log`) |
| :--- | :---: | :---: | :---: |
| **Corridas Exitosas** | 41 / 50 | 44 / 50 | **50 / 50** |
| **Exitosas al primer intento (sin deadlock)** | N/A | N/A | **45 / 50** |
| **Exitosas solo gracias al retry (intento 2 o 3)** | N/A | 0 / 50 (el retry nunca se disparó del lado correcto) | **5 / 50** (deadlock recuperado del lado Admin) |
| **Deadlocks sin recuperación (1213)** | 9 / 50 | 6 / 50 (todos del lado Admin, sin retry disponible ahí) | **0 / 50** |
| **Dobles Acreditaciones / Errores de Saldo** | 0 / 50 | 0 / 50 | **0 / 50** |

**Conclusión**: la v3 confirma la causa raíz identificada en 5.1 con evidencia verificable. De las 50 corridas, 5 sufrieron el deadlock InnoDB 1213 en el lado Admin y se recuperaron automáticamente gracias al retry recién agregado en `worker_admin.php` / `admin/partido_editar.php` (intento 2 o 3), sin ninguna doble acreditación. Las 45 corridas restantes tuvieron éxito directo sin deadlock. Esto es la prueba causal que faltaba: no es una mejora numérica sin explicación, sino el retry disparándose exactamente donde el deadlock realmente ocurre.

**Estado final**: BUG-001 **resuelto**, con las tres corridas (v1/v2/v3) documentadas como evidencia del proceso completo, incluyendo el paso en falso de v2 y su corrección.
